# demo/weekly-review — недельный разбор продуктивности

Реальный AI-пайплайн под конкретную личную задачу: **раз в неделю собрать в одном месте, что было
запланировано, что реально сделано и на что ушло время — и получить рекомендации по продуктивности**,
не сводя три приложения руками.

Источники — сервисы, которыми я пользуюсь:
- **[TickTick](https://ticktick.com)** — задачи (план и факт),
- **[aTimeLogger](https://atimelogger.pro)** — трекинг времени.

Собрано на наработках проекта: два MCP-сервера-обёртки над реальными HTTP-API + уже существующий агент
`cliJvmApp` (tool-loop + LLM) как оркестратор. Без судьи/FSM/RAG — только два MCP и агент.

## Как участвует AI

Агент по одной цели («разбери мою неделю») сам решает, что и когда вызвать:
1. `review_week` (ticktick-mcp) → план недели против факта: done / not done / gone;
2. `time_by_activity` (atimelogger-mcp) → сколько времени по типам активностей;
3. LLM сопоставляет план, факт и распределение времени и формулирует рекомендации.

Инструменты возвращают **только факты** — рассуждение и советы делает модель. Персона аналитика и формат
разбора заданы системным профилем `weekly` (`setup-weekly.sh`).

## Архитектура

```
                       cliJvmApp (агент + LLM Gemini)
                                │  tool-loop
             ┌──────────────────┴───────────────────┐
      ticktick-mcp                             atimelogger-mcp
   (Open API, OAuth2)                          (v2 API, Basic)
   snapshot_week / review_week                 time_by_activity
```

«Что сделано» — через **snapshot-diff**: официальный TickTick Open API отдаёт только незавершённые задачи
(и не умеет ни списка выполненных, ни тегов), поэтому `snapshot_week` в начале недели фиксирует план на
диск, а `review_week` в конце по каждому id проверяет статус (done / open / gone).

## Доступы (creds — только через окружение, в argv не передаются)

```bash
export ATIMELOGGER_USERNAME='...'   # логин/пароль аккаунта aTimeLogger (HTTP Basic)
export ATIMELOGGER_PASSWORD='...'
export TICKTICK_ACCESS_TOKEN='...'  # OAuth2 access token (см. playground/ticktick-mcp/README.md, scope tasks:read)
export GEMINI_API_KEY='...'         # если ключ не в local.properties (иначе берётся из BuildKonfig)
```

TickTick-токен добывается разово по OAuth2 authorization-code flow — пошагово в
[`playground/ticktick-mcp/README.md`](../../playground/ticktick-mcp/README.md). По условию задачи частичная
работоспособность из-за доступов допустима.

## Запуск

```bash
# 1) один раз: сборка бинарей + профиль weekly
bash demo/weekly-review/setup-weekly.sh

# 2) в НАЧАЛЕ недели — снимок плана (from включительно, to ИСКЛЮЧИТЕЛЬНО — день после последнего)
bash demo/weekly-review/snapshot-week.sh 2026-07-13 2026-07-20 2026-W29

# 3) в КОНЦЕ недели — разбор и рекомендации
bash demo/weekly-review/review-week.sh 2026-07-13 2026-07-20 2026-W29
```

Даты интерпретируются в зоне `WEEK_TZ` (по умолчанию — зона машины). Снапшоты лежат в
`~/.project01-mcplab/ticktick/snapshot-<label>.json`.

## Демо за один присест (для видео)

Двухфазность (снимок в начале, разбор в конце) можно показать сразу: снять снапшот → в приложении TickTick
закрыть 1–2 задачи из плана → запустить разбор — видно план/факт/время и рекомендации вживую. Отдельный
инструмент можно продемонстрировать напрямую:
`cliJvmApp -prompt "покажи типы активностей" -agent provider gemini mode system -mcpServer "<atimelogger bin>"`.

## Ограничения (честно)

- Задачи, **созданные и закрытые внутри недели** (не попавшие в снапшот), TickTick-частью не видны — их
  закрывает вторая половина картины (реальное время из aTimeLogger).
- **gone (404)** не отличает удалённую задачу от завершённо-заархивированной — помечается как «likely done».
- Нужен снимок в начале недели — задним числом неснятую неделю не разобрать.
- Точные имена полей ответов API подтверждаются по живому ответу (DTO defaulted + `ignoreUnknownKeys`).
