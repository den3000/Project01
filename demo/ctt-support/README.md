# CTT Support Assistant — демо

AI-ассистент поддержки пользователей продукта Corporate Task Tracker (CTT) на базе `cliJvmApp`.
Собран из готовых кирпичей: RAG по докам+коду, профили-персоны по фазам разговора, FSM из 5 стадий
с судьёй, MCP-сервер тикетов/пользователей.

## Роли

1. **Гость** — имени нет в `users.json`. Ассистент вежливо отказывает (проверка через `find_user`).
2. **Зарегистрированный** — есть в `users.json`. Ассистент помогает: ищет готовое решение в тикетах,
   диагностирует по документации; если не выходит — создаёт тикет (`create_ticket`) и передаёт
   разработке.
3. **Разработчик** — отдельный запуск `run-dev.sh` (сервер с `--dev`, профиль `developer`). Меняет
   статус тикета (`set_ticket_status`: `resolved`+решение / `wontfix`+причина). Право даёт сам запуск,
   а не токен в чате.

## Процесс (FSM + судья)

Стадии: `clarification` (кто/что) → `planning` (проверить прошлые тикеты) → `execution` (диагностика
по RAG) → `validation` → `done`.

Чат поддержки ведут три агента: **`support-intake`** (стадии `clarification..planning` — опознаёт
обратившегося и ищет готовое решение в тикетах), **`support-solve`** (стадии `execution..done` —
диагностирует по документации и эскалирует) и **`rules-judge`** на весь диапазон.

Нашёл судья нарушение — ход не выбрасывается: агент получает возражения и переписывает ответ. Прошло
— в чат идёт рерайт, стадия двигается, под ответом печатается блок `[invariant]` с возражениями и
пометкой, что первый ответ отозван. Не прошло и со второй попытки — ответ показывается, но в историю
не идёт и стадия держится.

Имя агента в `-agent <имя> …` — метка для читающего команду: движок её не потребляет (в теге
`[[AGENT:]]` печатаются профиль и модель). Стадийные агенты названы по своим профилям, чтобы в
команде и в выводе стояло одно слово; судья профиля не имеет, поэтому назван по роли.

**Почему профили нарезаны по фазам.** Судья аудирует ответ против `constraints` того профиля, с
которым говорил ответивший агент, — значит смена стадийного агента сама меняет мерило, и отдельный
судья на фазу не нужен. Один профиль на все стадии означал бы одно мерило на весь разговор:
ограничения фазы диагностики («называй источник утверждения») применялись бы и к приветствию.

**Как формулировать `constraints`.** Судья валидирует ход целиком: текст ответа, реплику
пользователя, выполненные за сессию вызовы инструментов, стадию и секции `format`/`style`. Истории
диалога у него нет, `context` профиля — тоже (там указания агенту, а не критерий приёмки).

Отсюда два правила формулировки:

- **Запрет, а не требование.** «Не приписывай продукту функций, которых нет в документации» верно на
  любой реплике; «отвечай только по документации» на фазе приветствия читается как нарушение.
- **Факт должен быть виден судье.** Имя клиента он находит в реплике, вызов `find_user` — в списке
  выполненных, а содержимое документации не видит нигде: она приходит агенту через RAG и в улики не
  попадает. Поэтому «не выдумывай пользователей и тикеты» — рабочий критерий, а «не приписывай
  продукту функций, которых нет в доках» — нет, судья проверял бы его своими знаниями.
- **Называй улику дословно, а не «подтверждение».** «…не подтверждённые поиском в базе» судья
  прочитал как «не подтверждённые пользователем» и забраковал перечисление тикетов, которые сам же
  признал вернувшимися из `list_user_tickets`. Формулировка «…которых нет в результатах выполненных
  вызовов инструментов» не оставляет места для толкования: есть в списке вызовов или нет.
- **Проверь формулировку против `context`.** Дважды подряд ограничение карало ровно то, что
  предписывала инструкция стадии: «передал разработке» против «не обещай», перечисление найденных
  тикетов против «сошлись на номер тикета». Судья `context` не видит и заметить конфликт не может —
  ловить его приходится при написании профиля.

Условных ограничений вида «**если** пользователь не найден — не переходи к диагностике» стоит
избегать даже теперь: решать «найден ли» судья будет догадкой, и один живой прогон на этом уже
потерян — честное «мне нужно ваше имя, чтобы помочь» было прочитано как намерение диагностировать
без проверки.

**Глобальных правил (`-rule`) у демо нет** — `setup.sh` только очищает список. Правило идёт в каждый
ход всем агентам, а все инварианты здесь фазовые и уже записаны в `constraints` своих профилей;
дубль в двух местах ничего не усиливает — судья получает и то и другое и на одно утверждение может
выдать два нарушения. Заводить правило стоит под инвариант, верный независимо от персоны и фазы.

## Содержимое

- `docs/` — 8 md-файлов FAQ о продукте (overview, installation, network-setup, tasks, api,
  auth-and-privacy, known-issues, troubleshooting). Индексируются вместе с отобранным кодом CTT.
- `users.json` — 5 зарегистрированных клиентов.
- `tickets.json` — 6 тикетов, статусы `new`/`in_progress`/`resolved`/`wontfix` + `resolution`.
  Два `resolved` (эмулятор→10.0.2.2; в CTT нет авторизации) — для переиспользования решений.
- `case-template.md` / `dev-case-template.md` — заготовки задачи (стадия `clarification`), которые
  обёртки кладут в память перед запуском.
- `setup.sh` — сборка + индексация RAG + профили (`support-intake`, `support-solve`, `developer`) +
  правила (один раз).
- `run-support.sh` / `run-dev.sh` — запуск чата (роль пользователя / разработчика), прячут
  многоагентную команду.
- [`../models.sh`](../models.sh) — общий для демо выбор моделей (`MODEL`/`JUDGE_MODEL`/…): каскад
  «роль → `MODEL` → дефолт клиента» и отсев 3.x/опечаток до старта JVM.

## Ключи

По умолчанию и агенты, и RAG-embedder — gemini: `GEMINI_API_KEY` должен быть в `local.properties`
или в переменной окружения (env перекрывает BuildKonfig). Экспортировать в скрипте не нужно.
Под `PROVIDER=ollama` ключ не нужен вовсе — и разговор, и эмбеддинг идут локально (см. «Запуск»).

## Запуск

```bash
# из корня репозитория Project01, один раз:
bash demo/ctt-support/setup.sh          # installDist + индексация RAG (жжёт embedding-токены) + профили

# чат поддержки (роль пользователя):
bash demo/ctt-support/run-support.sh

# консоль разработчика (смена статусов):
bash demo/ctt-support/run-dev.sh
```

Путь к репозиторию CTT для RAG-кода — переменная `CTT_REPO` (по умолчанию соседний каталог).
Нет каталога → корпус только из наших доков.

**Модели выбираются переменными** (пусто = дефолт клиента, `gemini-2.5-flash`):

```bash
MODEL=gemini-2.5-flash-lite bash demo/ctt-support/run-support.sh     # всем агентам разом
MODEL=gemini-2.5-flash-lite JUDGE_MODEL=gemini-2.5-flash \
  bash demo/ctt-support/run-support.sh                               # исполнители слабые, судья сильный
SOLVE_MODEL=gemini-2.5-flash bash demo/ctt-support/run-support.sh    # только диагностика
```

Роли: `FALLBACK_MODEL` (безпрофильный агент), `INTAKE_MODEL`/`SOLVE_MODEL` (стадийные агенты
`run-support.sh`), `DEVELOPER_MODEL` (`run-dev.sh`), `JUDGE_MODEL` (судья); конкретная роль побеждает
общий `MODEL`. Что реально поехало — строка `[demo] модели: …` перед стартом (и `[[AGENT:]]` в самом
чате). Семейство 3.x и опечатки в id отсекаются до старта JVM — механизм общий для демо,
[demo/models.sh](../models.sh).

**Провайдер — тоже переменной** (`PROVIDER=gemini` по умолчанию):

```bash
PROVIDER=ollama MODEL=qwen3.5:27b bash demo/ctt-support/run-support.sh             # локальная модель
PROVIDER=ollama OLLAMA_HOST=http://хост:11434 MODEL=qwen3.5:27b \
  bash demo/ctt-support/run-dev.sh                                                 # сервер не на localhost
```

Провайдер общий на прогон (у всех агентов сразу), под `ollama` модель обязательна: дефолтный тег
клиента вряд ли спулен, а вызывать инструменты умеет не всякий. Обёртка проверяет до старта JVM, что
сервер поднят, тег скачан и у него есть capability `tools` (`ollama show <тег>`) — иначе прогон
упёрся бы в отказ на каждом ходу. Печатается строкой `[demo] провайдер: …`.

**Индекс принадлежит провайдеру.** Под `ollama` корпус эмбедится локально (`nomic-embed-text`,
`ollama pull` обязателен) и лежит под именем `ctt-support-ollama`, под gemini — под `ctt-support`.
Смена провайдера требует своего `setup.sh`; два индекса живут рядом, поэтому переключаться туда-сюда
можно без переиндексации.

## Сценарии для видео

1. **Гость** — «Здравствуйте, я Пётр Незнакомцев, приложение не грузится» → `find_user` пусто →
   вежливый отказ, помочь не можем.
2. **Известное решение (переиспользование)** — «Я Ксения Иванова, эмулятор не видит сервер» →
   `find_user` находит USER-103 → `search_tickets` находит `resolved` TICKET-4415 → ассистент выдаёт
   готовое решение (10.0.2.2, SERVER_IP пустой).
3. **Новая проблема → эскалация** — зарегистрированный клиент с проблемой, которой нет в доках →
   диагностика по стадиям → `create_ticket` → ассистент называет номер и говорит, что передал
   разработке.
4. **Разработчик закрывает тикет** — `run-dev.sh` → «TICKET-XXXX, решено: …» → `set_ticket_status`
   resolved+решение.
5. **Возврат пользователя** — тот же клиент снова заходит `run-support.sh`, называет имя → ассистент
   через `list_user_tickets` видит, что тикет `resolved`, и сообщает решение.

## Замечания

- Судья удваивает вызовы LLM на ход (ответ + суд), а забракованный ход добавляет ещё два
  (переписывание + повторный суд) — учитывайте расход токенов.
- Ассистент не закрывает сессию сам: после эскалации называет номер тикета, вы выходите `/exit`.
- Один активный task-файл на id глобально → демо в один поток; обёртки сбрасывают кейс каждый запуск.
- Обёртки запускают с `-tui` (колонки `mcp │` / `rag │` отдельно от диалога). Для записи в один
  поток уберите флаг из обёртки.
- **`setup.sh` делает `-rule clear` — глобальные правила общие для всех демо**, так что правила,
  залитые другим демо, будут снесены. Профили чистятся по имени и не страдают.
