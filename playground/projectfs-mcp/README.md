# :playground:projectfs-mcp — файловый MCP-сервер по дереву проекта (read-write)

Standalone **MCP-сервер** (Model Context Protocol) по stdio: даёт ассистенту доступ к файлам
произвольного проекта — листинг, чтение, поиск, запись и точечная замена. На **Kotlin MCP SDK**
(`io.modelcontextprotocol:kotlin-sdk`). Пакет `ru.den.writes.code.agenticHub.mcps.projectfs`,
gradle-модуль `:playground:projectfs-mcp`. Не зависит на доменные/LLM-модули.

Закрывает дыру в инструментарии: RAG отдаёт похожие чанки, git-mcp — вид из VCS, но ни один не
открывает **произвольный файл, который модель выбрала сама**.

Спавнится MCP-клиентом подпроцессом. Аргументы: **первый — корень проекта** (по умолчанию — рабочая
директория процесса), **`--write-ext=` (опц.)** — список расширений, разрешённых к записи.
`main()` крутит сервер до отключения клиента (stdin закрылся). stdout — JSON-RPC; диагностика — в
stderr.

## Инструменты

Имена несут инфикс **`_project_`**: без него `list_files` столкнулся бы с одноимённым инструментом
git-mcp, а роутер клиента падает на дубликатах имён **на старте сессии** — уронив её целиком.

- **`list_project_files`** `{ "subdir"?, "ext"?, "limit"? }` — пути с числом строк
  (`README.md (155 lines)`), до 300 по умолчанию. Число строк — чтобы модель видела, влезает ли файл
  в одно чтение, и не тратила раунд на выяснение.
- **`read_project_file`** `{ "path", "offset"?, "limit"? }` — окно файла нумерованными строками
  (400 по умолчанию, 1000 максимум). Не дошли до конца — футер называет **точный** следующий вызов.
- **`search_project_files`** `{ "query", "subdir"?, "ext"?, "regex"?, "ignoreCase"?, "filesOnly"?,
  "maxMatches"? }` — совпадения как `path:line: text`. `filesOnly=true` — карта территории за один
  дешёвый вызов.
- **`write_project_file`** `{ "path", "content" }` — создать/перезаписать, ответ — unified diff.
  Для правки существующего документа есть замена: перезапись стоит его текста дважды.
- **`replace_in_project_file`** `{ "path", "old", "new", "replaceAll"? }` — точечная замена, ответ —
  unified diff.

### Отказ обязан учить

Инструмент, который на промахе просто говорит «нет», стоит раунда и ничему не учит. Дважды это
оказалось разницей между ассистентом, который продолжает работу, и тем, который останавливается:

- **пустой поиск** модель читает как «расхождений нет». Поэтому промах многословного запроса
  объясняет себя: запрос ищется **одной точной подстрокой**, а по отдельности слова встречаются вот
  в стольких файлах — бери термин оттуда. Счётчики собираются **в том же проходе**, что и поиск;
- **непрошедшая замена** отправляет модель гадать. Поэтому whitespace-зонд и зонд по первым 24
  символам называют похожую строку и точный `read_project_file(...)`, которым её перечитать.

## Безопасность

- **Гейт путей стоит до порта I/O.** `FileIo` принимает уже проверенные пути, поэтому фейк в тестах
  не может обойти защиту. Канонизация инъектируется → обход через `..` и симлинк наружу проверяются
  без реальной ФС.
- **Закрыты на чтение**: `.git/` (в `config` бывает токен в URL), `local.properties`, `.env`,
  `id_rsa`, `id_ed25519`, `secring.gpg`, `*.jks|keystore|p12|pem|key`. Закрытые пути **исчезают из
  листинга**, а не помечаются: запись `.env (закрыт)` сама по себе сообщает, что секрет есть.
- **Запись** дополнительно запрещена под `build/`, `.git/`, `.gradle/`, `.idea/`, `.claude/`,
  `node_modules/`, а `--write-ext=md` сужает радиус поражения до документации: правка `.kt`
  становится невозможной, а не просто нежелательной.

## Запуск

```bash
./gradlew :playground:projectfs-mcp:installDist
BIN=./playground/projectfs-mcp/build/install/projectfs-mcp/bin/projectfs-mcp
$BIN /путь/к/проекту                    # чтение и запись любых расширений
$BIN /путь/к/проекту --write-ext=md     # писать можно только .md
```

Подключение к ассистенту (cliJvmApp) — аргументы идут словами, т.к. `-mcpServer` бьётся по
whitespace:

```bash
cliJvmApp -mcpServer "$BIN /путь/к/проекту --write-ext=md"
```

## Раскладка

Всё под `src/main/kotlin/ru/den/writes/code/agenticHub/mcps/projectfs/`. Резать решено **по границе
инструментов**, чтобы тесты ложились один-к-одному:

| Файл | Роль |
|---|---|
| `main.kt` | argv → `runProjectFsServer` |
| `ProjectFsServer.kt` | только проводка: `addTool` ×5 + transport |
| `ProjectFsSchemas.kt` | конструкторы JSON-схем (`path`/`subdir`/`ext`/`limit` общие для инструментов) |
| `ProjectFsTools.kt` | слой диспетчера: JSON-аргументы → текст; **тотальность и лимит** |
| `ProjectPaths.kt` | гейт путей: containment, закрытые пути, гейт записи |
| `FileIo.kt` | порт I/O + `FileStat` + `RealFileIo` |
| `ProjectTree.kt` | шум/бинарники, отбор кандидатов, разбор `ext` |
| `ProjectText.kt` | чистые текстовые хелперы (строки, обрезка, снятие номеров) |
| `ProjectListing.kt` · `ProjectReader.kt` · `ProjectSearch.kt` · `ProjectWriter.kt` | тела инструментов |
| `ProjectHints.kt` | формулировки подсказок при промахе — чистые функции |
| `UnifiedDiff.kt` | LCS-диф с контекстом и склейкой ханков |

## Тесты

`./gradlew :playground:projectfs-mcp:test` — 152 теста, offline, на in-memory `FileIoFake`.

Фейк **повторяет реальный `walk`** и не отдаёт `build/`: фейк, который отдавал бы шум, вырастил бы
ниже по течению фильтр-ветку, до которой в бою не дойти, — и тест, проверяющий эту недостижимую ветку.

Живой путь — прогоном бинаря по JSON-RPC (`initialize` → `tools/list` → `tools/call`).

## Зависимости

`mcp-kotlin-sdk` + `serialization-json` (схемы инструментов) + `coroutines`. Ktor НЕ нужен — stdio
на `kotlinx-io`.

## Грабли

- **Корень — первый arg**; забыли → сервер смотрит на cwd (директорию клиента), не на проект.
- **`-mcpServer` бьётся по whitespace** — путь с пробелом развалится на два аргумента, и сервер
  получит не тот корень.
- **Лимиты живут только здесь.** Ниже по течению результат инструмента никто не обрезает: он целиком
  ложится в контекст модели. Поэтому `ProjectFsTools.respond` — единственная точка, где размер вообще
  можно ограничить, и через неё проходит каждый инструмент.
- **Исключение из инструмента рвёт ход клиента** (у хоста в `execute` нет catch) — поэтому наружу
  идёт только текст `projectfs error: …`, и это свойство закреплено тестом.
- **Один проход чтения на операцию.** `list` берёт размер и число строк одним `stat`; `read`/`search`
  страхуются дешёвым `size` (syscall) и читают один раз. Разделение этих вопросов — то, из-за чего
  листинг на 300 файлов стоил 300 полных чтений, а один пустой поиск — пяти проходов по дереву.
- **Поиск литеральный** (если не `regex=true`): у Java `\w`/`\b` только ASCII, и `\bЗадача\b` молча
  не найдёт ничего.
- **`ext` матчится суффиксом имени**, поэтому и `kts`, и `gradle.kts` находят `build.gradle.kts`.
  Раньше сравнивалась только часть после последней точки — `ext='gradle.kts'` не выбирал ни одного
  файла и отвечал «совпадений нет». Худший из возможных отказов: модель делала вывод, что термина
  в проекте нет, и записывала это как нарушение. Теперь фильтр, не выбравший ничего, говорит об
  этом прямо и перечисляет расширения, которые под этим путём есть.
- **Несуществующий `subdir` — тот же класс отказа, и лечится так же.** Прежняя короткая формулировка
  («под X нет файлов вовсе — проверь путь подкаталога») читалась слабой моделью как «поиск ничего не
  нашёл»: она объявляла это находкой и достраивала на ней выводы, пока не кончались ходы прогона
  (замер на сценарии `adr` — так сгорело целое плечо из трёх прогонов). Теперь сообщение называет
  причиной ПУТЬ, прямо отрицает вывод об отсутствии («пустой ответ НЕ означает, что искомого нет в
  проекте») и перечисляет каталоги верхнего уровня — чтобы у модели был выход из неверной ветки,
  а не ещё одна догадка.
- **Мусор десктопной ОС** (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `.localized`) не попадает в
  листинг: фильтр по имени, а не по расширению — у `.DS_Store` его нет.
- Номера строк снимаются с `old` **только когда пронумерованы все непустые строки** — иначе
  настоящая строка вида `42| foo` пострадала бы.
- `kotlin-logging` печатает строку инициализации **в stdout** до JSON-RPC — наш клиент это терпит,
  строгий парсер stdout может споткнуться (общая черта всех playground-серверов).
